# AirGap Mirror

AirGap Mirror 用来给**不能直接访问互联网的服务器**更新软件包。内网服务器导出一份状态文件，联网电脑按这份文件下载更新，再用移动硬盘把文件带回内网。

不需要让内网服务器直接上网，也不需要每次都搬运整个软件仓库。

## 一次更新怎么操作？

1. **在内网导出状态。** 在 Windows 客户端打开“连接服务器”，输入 Mirror Agent 地址和令牌。勾选需要更新的软件源，把状态文件（`.mstate`）保存到移动硬盘。
2. **在联网电脑下载。** 把移动硬盘带到能上网的 Windows 电脑，打开“联网下载”，选择刚才的状态文件和软件源。点击“查看需要下载的更新”，再把各批次下载到移动硬盘。中断后可以继续。
3. **回到内网导入。** 把下载好的批次文件夹带回内网电脑，在“离线导入”页面检查文件并导入服务器。如果有多个批次，就逐批导入。

两台 Windows 电脑可以不同：导入时可以直接读取移动硬盘中的批次文件，不要求使用原来下载时的电脑。

## 需要准备什么？

- **内网 Linux 服务器：** 运行 Mirror Agent，接收更新并管理仓库。Apache 可以继续提供软件包下载服务。
- **Windows 电脑：** 运行同一套桌面客户端，分别用于联网下载和内网导入。
- **移动硬盘或 U 盘：** 带出状态文件，带回下载好的文件。注意介质剩余空间及文件系统限制。

项目包含 APT、PyPI、npm 和 Maven 的适配器。Maven Central 同步的是指定依赖列表，不是整个中央仓库。

## 部署 Linux Agent

在项目根目录构建：

```bash
go build -o bin/mirror-agent ./cmd/mirror-agent
go build -o bin/mirrorctl ./cmd/mirrorctl
```

安装：

```bash
sudo ./scripts/install-agent.sh
```

启动 Agent 需要设置连接令牌 `AIRGAP_MIRROR_TOKEN`，并在服务器上配置软件源及其仓库目录。Apache 和 systemd 的配置示例见 [部署说明](docs/DEPLOYMENT.md)。

## 遇到问题时

- **连不上服务器：** 检查 Agent 是否在运行、地址和端口是否正确，连接令牌是否一致。
- **下载中断：** 回到原来的下载任务，选择同一个保存位置继续。不要删除未下载完的文件包。
- **提示软件源正在同步：** 先完成已有任务。已经写入服务器的任务不能随意取消。
- **想释放服务器空间：** 展开“连接服务器”页面里的维护工具，先预览可能不再需要的文件，再决定是否删除。

## 实现和限制

Windows 客户端采用 Wails v2、React 和 TypeScript，Linux Agent 使用 Go；SQLite 保存同步状态，实际文件保存在原生仓库目录中。项目 CI 会运行 Go 测试、Linux 构建和 Windows 桌面端构建。

**APT 联网分析会验证发行版的官方仓库签名。** Ubuntu 和 Debian 的官方签名公钥随程序提供，Windows 联网电脑无需安装 GnuPG。Linux 内网发布前还会独立验证上游签名。

更多部署信息见 [部署说明](docs/DEPLOYMENT.md)。其他设计文档只供参考，实际行为以源码为准。

## Linux 服务器的浏览器管理界面

更新 Agent 后，在服务器上运行安装脚本，再用配置脚本设置实际监听地址：

```bash
sudo bash scripts/install-agent.sh
sudo bash internal/server/web/configure-agent.sh --listen 192.168.21.4:8787
```

如果 Linux 服务器的 IP 是 `192.168.21.4`，可从可信内网浏览器打开 `http://192.168.21.4:8787/`。这是示例地址，更换服务器时请使用对应 IP。页面需要输入 Agent 的连接令牌。配置脚本只设置 Agent 监听地址，不修改 Apache、仓库文件或防火墙规则。

**已经使用 Apache 反向代理的旧服务器请保留原来的域名。** 例如旧地址是 `https://mirror.costar.com/mirror-control`，新版 Linux WebUI 使用 `https://mirror.costar.com/mirror-control/`（结尾带 `/`），Windows 客户端仍可填写原来的 Agent URL。Agent 应继续只监听 `127.0.0.1:8787`，不需要运行 `--listen 192.168.21.4:8787`。Apache 的 `ProxyPass /mirror-control/ http://127.0.0.1:8787/` 保留不变。建议将无结尾斜杠的 `/mirror-control` 重定向到 `/mirror-control/`，避免浏览器相对路径失效。


以上命令适用于从 GitHub 源码仓库克隆并构建的情况。若使用 `v*` Linux 发布包，配置脚本位于 `scripts/configure-agent.sh` 和 `scripts/configure-apt-signing.sh`。两份脚本也可在已安装的 Linux Web 管理页面直接下载，再复制到离线服务器运行。

### 检查统计后为 APT 仓库重新签名

先从 Linux 管理页面运行“重新清点文件”，等清点任务完成并确认文件数与容量。需要重新签名时，先由管理员运行：

```bash
sudo bash internal/server/web/configure-apt-signing.sh
```

此脚本在 `/var/lib/airgap-mirror/gnupg` 为服务用户创建/选定专用密钥，管理员需要明确同意创建；不会偷偷在客户端添加信任。再回到 Web 管理页面点击“检查后重新签名”，重新生成内网 APT 的 `Release`、`Release.gpg` 和 `InRelease`。签完后下载公钥，按客户端仓库配置将其安装为专用受信任密钥（不要将私钥拷走）。

**重要：本地重新签名与联网端验证上游签名是两个独立过程。** 本地清点和重新签名不证明已有文件来自可信上游。内网 Agent 在发布 APT 更新前独立复核上游签名；本地重新签名仍需 Linux 上的 GnuPG。

### Windows 下载恢复

程序现在会在打开联网下载页面时查找未完成的任务。原来已下载完成的批次可以保留；丢失或损坏的批次可以选择“重新下载这一批”。默认单批约 8 GiB、文件包约 1 GiB，适合更多移动硬盘。对于超过单个文件包大小的制品，仍须使用支持大文件的移动介质。


### 大型 PyPI 仓库分段清点与断点恢复

PyPI 清点按 `simple/<project>/index.html` 中的项目逐个检查，使用独立的 SQLite 临时账本。每完成 100 个项目保存一次原子检查点（项目位置、文件数量、容量及对应文件记录一起提交），已完成的检查点在暂停或 Agent 重启后保留。Linux WebUI 和 Windows 维护工具都可使用“继续清点”，或“放弃清点”删除临时账本。

- 只有全量检查成功后才用单次数据库事务替换正式 Catalog；暂停/异常期间旧 Catalog 保持不变。
- 检查点不是逐字节校验几十 TB 的包内容：主要解析项目索引、校验文件是否存在及大小；文件哈希取自项目索引。支持随时停止，但最后不足 100 个尚未提交的项目需要重查。
- 若源设置、项目目录成员或已检查项目的索引文件发生变化，为防止遗漏项目，会拒绝发布陈旧清单；需要放弃旧清点并重新开始。扫描期间不要在外部修改仓库目录。
- 暂停的任务继续占用这个软件源的维护位置，避免与下一轮导入混杂。若不再继续，请先点击“放弃清点”再开始新的同步。


### Catalog 分代发布与 PyPI 缺失文件修复

旧数据库中的文件账本不需要在升级时全量迁移。新清点结果先按 10000 条记录分批构建独立代际，写入位置与数据一起提交；最后在一个小事务中切换当前 Catalog、更新统计与清点任务状态。旧版本只作为历史数据保留，不会自动回滚仓库或删除软件包。新账本仍要从清点临时数据库分批复制一次，构建时应为临时文件、旧代和新代以及 SQLite 日志预留空间。暂不自动回收旧代；不要手工删除数据库内部记录。

PyPI 已有正式 Catalog 的软件源可使用“检查缺失文件”。每 1000 条记录保存检查点，Agent 重启后可继续；检查存在性与文件大小，不是逐字节哈希校验。完成后查看异常，导出修复状态文件（schema 2，需要新版 Windows 客户端），按原来的联网下载和离线导入流程操作。修复分析会主动加入缺失文件所属项目，即使上游 serial 没有变化也会下载仍能取得且与原账本散列、大小一致的包。正式 Catalog 在检查和导出时不修改。大小不符的文件仅报告，不自动覆盖；上游已移除的文件需要可信备份。该检查基于已有 Catalog，不能替代首次清点或发现从未入账的文件。状态文件可通过维护页面的导出任务生成，Agent 重启后未完成的导出任务会重新生成。


### 历史 Catalog 回收与大型状态文件导出

- 维护页面中的“回收历史账本”在软件源空闲时每次最多删除 5000 条已退役或已取消/失败任务的历史记录。它不删除任何软件包、不修改正式 Catalog、不删除暂停任务的检查点。可中断并重新执行。回收需要手动确认，历史版本回收后不可恢复。SQLite 数据库空闲页会被后续写入复用，文件大小不一定立即缩小；不会自动执行全库 VACUUM。升级到分代 Catalog 后请备份数据库，不能通过直接换回旧二进制文件安全降级。
- 新的导出任务在 Agent SQLite 中保存，WebUI 与 Windows 维护工具可查看队列、阶段、进度、失败原因及下载已生成的文件。请求断开不会取消任务；Agent 重启后未完成的任务重新排队并从头生成该状态文件（不是压缩流断点续写）。每次导出仍生成完整一致性快照，旧版同步导出 API 保留兼容。
- Windows 状态文件下载通过 HTTP Range 和 ETag 验证续传。若下载中断，在维护页面选择同一个已完成的任务和目标路径继续，保留 .part 与 .part.json。支持文件保存接口的 HTTPS 浏览器直接把文件流写入磁盘；不支持该接口的浏览器仅允许较小的状态文件下载，建议使用 Windows 客户端处理超过 512 MiB 的文件。
- PyPI 的清点检查点会在完成一个项目后按累计 100 个项目、10000 个记录或 15 秒（任一条件）提交。单个未完成项目仍需要重新检查。完整增量清点仍需设计可验证的逐项目文件引用关系，不以索引时间戳代替文件存在性检查。


### PyPI 完整性校验

在维护页面选择“SHA256 完整校验”，输入读取速度上限（1–1024 MiB/s，默认 64）。快速缺失文件检查仍只检查存在性和大小；完整校验读取大小正常的已入账文件，计算 SHA256 并与 Catalog 中的预期值比较。记录缺失、大小不符和 SHA256 不符三种异常。每 32 个文件、累计 256 MiB 的账本大小或 5 秒，在完整文件边界保存检查点。暂停和 Agent 重启后从已保存的位置继续，当前未完成的大文件须重新读取。限速为每任务近似上限，不是服务器全局 I/O 限速。

校验期间不修改文件或正式 Catalog，不应从外部修改仓库文件。报告中的大小或 SHA256 不符记录仅用于诊断，不会自动删除或覆盖文件；修复状态文件仍只针对缺失文件。若需要恢复损坏文件，须先确定可信备份或上游内容，完成单独的安全替换流程。完整校验可能持续多天，请按存储性能选择速度。


### 已授权的 PyPI 损坏软件包修复

完整性校验完成后，在维护页面查看异常并选择“授权损坏文件修复”，再导出修复状态文件。已授权报告中的、实际 SHA256 已记录的大小异常或哈希异常软件包会与缺失文件一起加入离线修复计划。授权只适用于 PyPI 的 packages/ 文件，不自动授权项目索引或其他仓库。此前仅记录大小异常、未记录实际 SHA256 的报告需重新做完整校验。每个软件源同一时间仅允许一个报告授权；软件源配置或正式 Catalog 版本变化后授权失效。可在软件源空闲时撤销。

导入时 Agent 根据服务器保存的报告和当前正式账本重新验证授权及软件包身份，不信任离线包自行声明的替换权限。旧文件的大小和 SHA256 必须仍与报告一致；新文件完整写入同目录临时文件、验证正式账本要求的大小及 SHA256 并同步到磁盘后，使用硬链接保留旧文件，再原子重命名替换。隔离目录为仓库内 .airgap-staging/repair-quarantine/<报告ID>/<随机ID>/<原相对路径>，权限 0700；需确保 Apache 不对外提供 .airgap-staging，禁止外部程序并发修改仓库。跨文件系统或不支持硬链接的存储会拒绝替换。隔离文件保留，暂不自动回收。普通未授权导入仍拒绝同路径不同内容。若上游已移除原软件包或其内容与正式账本不一致，拒绝生成修复计划，需要可信备份。损坏文件修复不改变原有同步游标机制，也不能替代全量或增量清点。


### PyPI 增量清点（开发中）

在全量清点或增量清点完整成功后，Agent 在 maintenance 目录保留每个软件源最近一份只读项目清点缓存。增量清点按项目索引实际 SHA256 判断是否可以复用记录；仍逐个检查引用文件存在性及大小，不使用索引修改时间作为复用依据，也不等同于完整 SHA256 软件包校验。没有缓存、索引变化或跨项目共享文件导致引用集合不完整时重新解析索引。首次增量清点可以自动退化为全量解析。新项目加入、已删除项目移出新账本，正式 Catalog 仍仅在全部成功后原子切换。暂停后继续会在发布前重新检查已入账文件的存在性及大小。外部程序仍不得并发修改软件源目录。

缓存是一份额外的 SQLite 文件账本，需预留相应空间；每个软件源仅保留最近一份成功清点缓存，不包含软件包内容。若缓存损坏或需要完全重新生成，请选择全量清点。缓存不替代数据库备份，也不跳过软件包存在性检查。

### APT 仓库签名验证

内网创建软件源时只需配置仓库目录、内网访问地址及软件源本身的设置。Windows 联网下载页根据状态文件中的软件源类型和发行版提供官方源、常用镜像站及自定义公网地址。查询上游和生成下载计划使用选定的地址，旧状态文件仍可使用，不必重新导出。已生成的下载任务保留原计划中的文件地址。Ubuntu 和 Debian 根据发行版代号使用内置的官方归档公钥，无需用户获取公钥、转换 Base64 或在联网电脑安装 GnuPG。公钥来自 Ubuntu 的 ubuntu-keyring 和 Debian 的 debian-archive-keyring 官方软件包，保存在程序内，不从所选镜像站下载。已有自定义公钥配置仍然有效；其他发行版或第三方仓库暂不提供自动公钥配置。

程序内部验证 InRelease 或 Release/Release.gpg，检查签名者、签名与密钥有效期、SHA256 或更强的摘要、Release Date、Suite/Codename 及已声明的 Valid-Until。未知或无效的签名会导致更新停止，不会跳过验证。密钥轮换时更新程序即可。原有软件源和状态文件中没有自定义公钥的 Ubuntu、Debian 配置也可使用默认官方公钥。

默认允许未声明 Valid-Until 的稳定仓库；已有特殊有效期要求保持不变。缺少 Valid-Until 时仍可能存在历史签名快照被重放的风险，当前没有单调版本或时间防回退机制。

### APT 内网发布前独立验证（开发中）

Agent 在发布任何 APT 元数据前，使用程序内置的官方公钥或已有自定义公钥配置验证待发布的 InRelease 或 Release/Release.gpg；与同步目标游标核对，并对 Release 所列索引及 by-hash 文件逐个校验实际 SHA256。优先读取暂存文件，已完成重命名的文件从正式目录读取以支持中断重试。解析经过验证的 Packages/Sources 索引并核对文件大小、存在性及 Catalog 中的 SHA256；拒绝不属于签名 Release 的元数据。联网端非空更新携带上游签名文件，以便内网独立验证。Agent 验证上游签名无需调用 GnuPG；只有内网仓库的本地重新签名功能仍需安装 GnuPG。非元数据文件限制在 pool/ 中，此阶段适用于标准 Debian/Ubuntu 式仓库。

本阶段不是全量软件包内容复核：新导入软件包由现有 Pack 导入校验字节，已有软件包按 Catalog 和大小检查；完整性校验和签名传输协议仍需进一步开发。APT 包池文件仍在导入阶段写入，发布前验证失败会保留旧元数据，但已导入的新包可能留在包池；尚未实现整仓库原子发布、独立签名传输包或历史快照防回退。上游 Valid-Until 在内网发布时也必须有效。旧版或本地重新签名的元数据不是上游签名证据，已有任务可能需要使用新版联网端重新生成同步计划。
